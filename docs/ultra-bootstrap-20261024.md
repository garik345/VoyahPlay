# Климат, автомобиль и радио появились в CarPlay

Проверка по ADB 24.10.2026, 11:17–11:53 +0300, устройство d6bfd312.
Итоговая установленная сборка: **opack-23-fan-wire**, automotive/debug.

Следующая сборка [opack-24-climate-state](ultra-climate-state-20261024.md)
подготовлена с изменениями рециркуляции и вентиляции сидений; на машину пока не установлена.

Подтверждено изображением с мультимедиа: в меню iPhone появились приложения
**«Автомобиль», «Климат», «Радио»**, температура обеих зон в доке и управление климатом.
Это интерфейс внутри видео CarPlay, отдельно от штатных боковых кнопок Android.

## Результат по четырём пунктам

| Проверка | Результат |
| --- | --- |
| displayPanels / plugins | Отдельный опыт opack-19 с логическим инструментальным плагином принят телефоном, но сам по себе кнопки не открыл. |
| UI Sync | Найден и исправлен неверный формат обработчика. Новая реализация использует OPACK с вложенными binary plist и числовыми типами. Шифрованные сокетные тесты проходят. На реальном iPhone CarPlayClusterControl пока не открывался. |
| Тема / ресурсы | Добавлены themeAssetIdentifier при iAP2 Identification и SDK/asset/version в CarPlayStartSession. После включения диагностической темы появились все три приложения. |
| Настоящие кнопки климата | Через UI iPhone проверены температура, вентилятор, A/C и восстановление AUTO. Успех подтверждён обратным чтением CAN. |

Главный установленный дефект запуска UI — отсутствовавшее объявление темы.
Работающий CAF и согласованный флаг uiSync сами по себе не включали этот интерфейс.
Появление главного климата без CarPlayClusterControl также опровергает предположение,
что открытие этого канала обязательно для кнопок климата на центральном экране.
Работа UI Sync с реальным телефоном остаётся отдельной непроверенной частью.

## Тема: что именно изменено

По первичному коду LIVI, commit `f999f55735278acd76f0fa207218cac00a739047`:

- Identification: поле 6 внутри USBHostTransportComponent / WirelessCarPlayTransportComponent.
- CarPlayStartSession 0x4301: поле 6 — SDK, группа 7 — identifier (0) и u32 version (1).
- Идентификаторы экрана должны соответствовать пакету и совпадать в displays,
  HID displayUUID, displayPanels, initialVideoStreams и последующих командах дисплею.

Для локального опыта используется пример LIVI **44C9FA31EC:985:19.0**.
Его наличие и версия проверены в каталоге Apple `com.apple.MobileAsset.CarDDPAssets`.
Из ZIP прочитаны только package.json и theme.json: там подтверждены Center_Display,
Cluster_Display и центральный размер 1920×720 при 157 dpi.
Пакет изображений не включён в APK. Название, идентификатор, производитель и модель
самого приёмника этим опытом не подменялись.

Это **диагностическая сторонняя тема, не готовая тема Voyah**. Она включается скрытым
debug-параметром `themeProbe`, по умолчанию false. Release-заглушка возвращает null.
На проверенной мультимедиа параметр оставлен true, поскольку с ним работает UI.
Также сохранены enabled=true, mutualAuth=true, assetProbe=false, panelProbe=true.
Для выключения опыта достаточно themeProbe=false и перезапуска приёмника;
для полного возврата исходной конфигурации панелей также panelProbe=false.

Сначала использовался прежний поток 1556×674: тема открыла климат, но её раскладка
обрезалась. Диагностическая конфигурация теперь объявляет 1920×720, 311×116 мм;
видео и координаты касаний масштабируются существующим приёмником. Для этого опыта
не применяются пользовательские viewAreas и квадратный холст поворота. Сохранённые
настройки размера/поворота не переписываются.

## UI Sync

Старая реализация отправляла строковые enum-имена в плоском plist и сама начинала RESET.
В работающем пути теперь используется:

1. OPACK-словарь с displayUUID и data=bplist(header); дополнительные поля маршрута сохраняются.
2. Числовые типы RESET=0, RESET_COMPLETE=1, COMMAND=2, COMMAND_ACK=3.
3. Ожидание RESET от iPhone; сохранение его id; согласование версии максимум 2.
4. После RESET_COMPLETE — allowLayoutChange (0x11, allow=true) и giveFocus (7, tokenID=4711).
5. Команды лежат ещё в одном plist в header.data. Поддержаны noAck, подтверждение,
   возврат фокуса по requestFocus и защита от повторного выполнения команды.

Не выбираются вымышленные layoutID и не создаётся дополнительный видеопоток.
Транспортный sync/rply проверяется отдельно. Ошибки и TEARDOWN UI Sync изолированы от CAF.
Старый CarPlayUiSyncProtocol.kt оставлен как историческая символическая модель;
активный обработчик им не пользуется.

## Проверка кнопок на машине

После подтверждения пользователем, что автомобиль припаркован:

| Действие внутри CarPlay | Обратное чтение |
| --- | --- |
| Температура 23 → 23,5 → 23 °C | Оба writeRequest iid=11 подтверждены; обе зоны вернулись к 23 при штатном SYNC. |
| A/C выкл → вкл → выкл | confirmed=true для обеих команд; AUTO после опыта восстановлен. |
| Вентилятор 3 → 4 → 3 на итоговой сборке | FAN=4 readback=4, FAN=3 readback=3; около 268–269 мс; затем AUTO=true подтверждён. |
| «Автомобиль» | Открывает страницу с громкостью и сведениями VoyahPlay / opack-23-fan-wire. |
| «Радио» | Открывает native FM/AM со списком реальных станций. В dashboard также наблюдались FM 107.0 / MARUSYA и FM 98.0 / CHOCOLAD. |

Проверка выявила ошибку вентилятора: прямой TX31 раньше передавал уровень кэша,
а OEM onAdjustWindVolume передаёт `level + 1`. Запросы 4 и 2 возвращались как 3 и 1.
Исправлено преобразование 0…7 → 1…8 и верхняя граница CAF. Повторная проверка выше
выполнена уже после исправления. Подробности в [разборе OEM HVAC](oem-hvac-20261020.md).

В конце контрольных действий восстановлены температура 23 °C, вентилятор 3,
AUTO=true, A/C=false. Подогревы/вентиляция сидений в эти проверки не входили.
