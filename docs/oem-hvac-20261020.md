Исходная подсказка о штатных методах — [VoyahTune: OEM Vehicle APK](https://github.com/nexron171/VoyahTune/blob/f1a99cd9d467232d6e0aee9db633342f52b7c0b4/Docs/oem-vehicle-apk.md).
Этот документ действительно описывает HVAC. Полный путь проверен по присланным бинарникам,
а не только по наличию имён в SDK.

`vehiclebase.model97.controller.AirConditionControl` → `CanBusManager.setAirConditionState`
или `setAirConditionStateEx` → `ICanBusService` TX31 → проверка WRITE_CANBUS →
`DongfengH97CCanBusComponentImpl.setAirConditionState` → `FillCommand` / `sendCanIOCtl`.
Factory выбирает H97C для типов 134, 13401, 13402. Проверена именно эта ветка.
Возвращаемый SDK-код 0 означает завершение Binder-вызова; подтверждение состояния требует TX30.
TX33 обрезает дробную температуру до целого, поэтому для обратного чтения используется полный TX30.

| Функция CAF | AirConditionState | ordinal / id | Параметр TX31 | Поле TX30 |
| --- | --- | --- | --- | --- |
| Температура водителя | AC_LEFT_TEMP | 2 / 3 | 15.5…30.5 °C × 10; шаг 0.5 °C | airLeftTemperature |
| Температура пассажира | AC_RIGHT_TEMP | 3 / 4 | То же | airRightTemperature |
| Питание климата | AC_POWER_SWITCH | 7 / 8 | Импульс 1, если состояние отличается | airSWStatus, 0/1 |
| A/C | AC_SWITCH | 4 / 5 | Импульс 1, если состояние отличается | airACStatus, 0/1 |
| AUTO | AC_AUTO | 6 / 7 | Импульс 1, если состояние отличается | airMode, 0/1 |
| Вентилятор | AC_BLOWER | 0 / 1 | Уровень кэша 0…7 + 1 → TX31 1…8 | airWindSpeed |
| Рециркуляция | AC_RECIRC_AIR | 10 / 11 | Импульс 1; проверка перехода режима | airCirculationMode: 0 внутренняя, 1 внешняя, 2 AUTO — по штатному экрану |
| Переднее стекло | AC_FRONT_DEFROST_SWITCH | 8 / 9 | Импульс 1, если состояние отличается | airFrontWindowDefogger, 0/1 |
| Заднее стекло | AC_REAR_DEFROST_SWITCH | 9 / 10 | 0 выкл, 1 вкл; сервис преобразует в 1/2 | airRearWindowDefogger, 0/1 |

Импульсные вызовы дополнительно сверены с `VoiceAirConditionListener`, его callback
`onAirConditionChanged` и `VoiceDemistListener` в model97. Они не равнозначны записи 0/1.
Для рециркуляции разрешено максимум два импульса: второй только после подтверждённого перехода
между известными кодами 0/1/2. При неизменившемся или неизвестном ответе повтор не посылается.
Порядок цикла заранее не предполагается. Уточнение opack-31: AirConditionFrontFragment
рисует для 0 внутреннюю, для 1 внешнюю циркуляцию; голосовой обработчик подписывает
их противоположно. Приоритет у отображаемого штатного экрана. Для подтверждения
ручного выключения требуется режим 1, включения — 0. AUTO не сообщает положение
заслонки; с opack-31 необязательный CAF AutoMode убран, чтобы AUTO не подсвечивал
кнопку как включённую рециркуляцию.
[Разбор противоречия и подготовленная сборка](ultra-recirculation-rear-window-20261025.md).
Подробности и границы проверки: [рециркуляция и вентиляция сидений](ultra-climate-state-20261024.md).

Температуру масштабируем ровно один раз: SDK `setAirConditionStateEx` делает умножение ×10,
а наш прямой Binder-вызов передаёт уже 225 для 22.5 °C. Не передавать 225 в SDK Ex.

Уточнение 24.10.2026: `VoiceAirConditionListener.onAdjustWindVolume` ограничивает
уровень кэша максимумом 7 и вызывает `setWindSpeed(level + 1)`. CAN-сервис ограничивает
параметр AC_BLOWER максимумом 8. Прямую передачу уровня без +1 опровергла проверка
из настоящего CarPlay: запрос 4 вернул 3, запрос 2 вернул 1. CAF теперь описывает
диапазон кэша 0…7; прибавление выполняется только на выходе в OEM, чтение не сдвигается.

MAX A/C, DUAL/SYNC, направления потоков, задняя зона и другие функции не добавлены в CAF
как рабочие кнопки этого этапа. В частности, AC_MAX_SWITCH есть в SDK, но не обрабатывается
проверенным H97C setter. Наличие константы не считается доказательством поддержки.
Датчик температуры салона не подменяется заданной температурой.

## Описание для iPhone

Сверка контрактов и типов: [LIVI vehicle_state.rs](https://github.com/f-io/LIVI/blob/3fb5210f71ebc4b15d9aed034df8f0c28eda4f54/native/livi-helperd/crates/livi-cp/src/vehicle_state.rs)
и [displayPanels в info.rs](https://github.com/f-io/LIVI/blob/3fb5210f71ebc4b15d9aed034df8f0c28eda4f54/native/livi-helperd/crates/livi-cp/src/info.rs).
Независимая Kotlin-реализация использует сведения о формате; Rust-код не переносился.

`/info` и configResponse описывают одну схему: pluginID 0, две Temperature-зоны с
VehicleLayoutKey, Cabin, Fan, AUTO, Recirculation, WindowDefrost, VehicleResources/5Seater,
а также прежние подогревы/вентиляцию сидений и руль при доступном WRITE_CANBUS.
Панели ссылаются только на реальные видеопотоки. На этапе этого разбора UI Sync не заявлялся.
Начиная с opack-13-uisync он подключён отдельно: [текущее поведение и проверки](ultra-uisync.md).

Обнаружена отдельная ошибка: AirPlaySession прежде строил `/info` через общий прототип расширения,
тогда как CAN-данные хранились в экземпляре сессии. Теперь используется расширение этой сессии.
Проверка воспроизводит настоящий обработчик GET /info и отличает прототип от экземпляра.
Это подтверждённое исправление кода; его достаточность для появления меню iPhone ещё не проверена.

Запись разрешена только после явного writeRequest, проверки типов/диапазона, доступа WRITE_CANBUS,
хеша CAN APK и свежего снимка поддерживаемой машины. Чтение, подписка, `/info` и подключение
не запускают физические команды. Успех CAF выдаётся только после совпадения обратного чтения.
Невалидные параметры: -50; неподтверждённое выполнение: -6727. Это не атомарная транзакция
нескольких автомобильных функций. Возраст снимка — время чтения OEM-кэша, не время измерения датчиком.
